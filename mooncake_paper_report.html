1他们要解决什么问题

Kimi 是长上下文起家的 MaaS。这个业务形态给推理系统出了三道题，恰好是学术界当时都没答的：

难题为什么难Mooncake 的回答
① 长上下文的 prefill 极贵 attention 计算量随输入长度平方增长。trace 里平均输入 7,590 tokens、输出只有 182——输入输出比约 720:1，prefill 就是成本大头 能复用的 KVCache 绝不重算（前缀缓存），单条超长请求用多机流水线并行（CPP）压 TTFT
② 吞吐优化和延迟 SLO 天然打架 复用远端 KVCache → 传输拖长 TTFT；攒大 batch 提 MFU → TBT 变差。两个提吞吐的手段都会踩延迟红线 调度目标改成"在 TTFT/TBT SLO 约束下最大化有效吞吐（goodput）"，而不是裸吞吐
③ 常态过载 用户增长远快于 GPU 到货。学术界的假设"所有请求都会被处理"在 Kimi 不成立 过载调度作为一等设计：预测负载、提前拒绝注定完不成的请求，别让 GPU 白算
关键定义 · goodput

论文对 goodput 的口径比同类工作更狠：只有完整跑完全程的请求才计入吞吐。一个请求 prefill 算完了、decode 中途被拒，之前消耗的所有 GPU 秒全部记为浪费。这个口径直接推出了后面整套 early rejection 的设计——"要拒就趁早拒"从口号变成了数学必然。

2架构总览：四个角色

Mooncake 不只是"P/D 分离"。它把 GPU 集群里闲着的 CPU、DRAM、SSD、RDMA 网卡也组织起来，形成第三个池——分布式 KVCache 池。四个角色：

┌────────────────────── Conductor（全局调度器，大脑）──────────────────────┐ │ 每个请求：选 (prefill 节点, decode 节点) 对；顺带决定 KV 块的复制/换出 │ └──────────────┬──────────────────────────────┬───────────────────────────┘ ▼ ▼ ┌─────────────────────┐ ┌─────────────────────┐ │ Prefill 池 │ KV 流 │ Decode 池 │ │ 目标: 复用KV、压TTFT │ ─────▶ │ 目标: 攒大batch提MFU │ │ 约束: TTFT SLO+DRAM │ │ 约束: TBT SLO+VRAM │ └──────────┬──────────┘ └──────────┬──────────┘ │ ▲ │ ▼ │ (GPUDirect RDMA) ▼ ┌──────────────────────────────────────────────────────┐ │ 分布式 KVCache 池（CPU DRAM/SSD 分页存储, 前缀链哈希去重）│ │ 搬运工: Messenger（每节点独立进程, 收信号跨机高速传 KV） │ └──────────────────────────────────────────────────────┘

几个容易被忽略的要点：

① P 池和 D 池的目标函数是相反的。Prefill 是算力密集（计算时间随输入超线性涨），追求复用 + 压 TTFT；Decode 是访存密集（一次只出一个 token，计算时间随 batch 亚线性涨），追求大 batch + 守 TBT。放一起（vLLM 式耦合）就是长 prefill 打断 decode 的根源。

② KV 块的身份是"前缀链哈希"。每 512 tokens 一块，块的 hash 包含自己 + 全部前缀的 hash——两个块 hash 相同 ⇔ 从头到这块的所有 token 完全一致，即可复用。这也是开源 trace 里 hash_ids 字段的语义。

③ Conductor 不只路由请求，还调度 KV 块本身。热块复制到多台机防拉取拥塞，冷块换出省容量——请求调度和块放置是同一个大脑的两只手。

3一个请求的一生（4 步 workflow）

步骤做什么关键细节
1. KVCache 复用选中的 prefill 节点按前缀块 ID 从远端 CPU 内存把可复用 KV 拉进 GPU选点同时平衡三件事：复用最多 / 各节点负载均衡 / TTFT SLO 兜住（§5 算法）
2. 增量 prefill只算未命中的部分；超过 prefill_chunk（>1000 tokens）就切块流水线执行chunk 阈值选到刚好吃满 GPU 算力——保 MFU 的同时不给单请求过度切碎
3. KV 传输Messenger 把每层算出来的 KV 逐层、异步流式发往 decode 节点的 CPU 内存与步骤 2 完全重叠——传输延迟被计算隐藏（§4.2 layer-wise）
4. DecodeKV 全部到齐后加入 decode 节点的 continuous batching⚠️ decode 侧本地调度器会 double-check TBT SLO——预估的负载可能已经变了，此时拒绝 = prefill 白算（这正是 early rejection 要消灭的浪费）
映射 → 我们的 DESIGN.md

步骤 4 的 double-check 浪费，就是我们 §4 里 Gated-PD / D-reserve 要解决的同一个问题。Mooncake 的答案是"把 D 侧评估提前到 prefill 开始前"（预测式，§7）；Gated-PD 的答案是 probe+COMMIT（测量式）；Mooncake Store 化后则是"KV 停在池里等 D"（结构性消解）。三条路线在 DESIGN.md §4.3 路径表里分别是 D、B、D/E。

4Prefill 池的两个硬核设计

4.1 Chunked Pipeline Parallelism（CPP）：长上下文多机并行的"务实解"

128K/1M 上下文的单条请求，一台 8 卡机压不住 TTFT，必须多机。当时的候选方案：

方案问题
跨机 Tensor 并行（TP）每层要 2 次跨机 all-reduce，RDMA 也扛不住，prefill MFU 掉得厉害
序列并行（SP，Ring/Striped Attention）比跨机 TP 好，但仍每层至少通信一次；且"短请求走 TP 组、长请求走 SP 组"的分组架构需要频繁弹性伸缩两个组的规模——线上运维噩梦，还和 KV 传输抢网络
CPP（Mooncake 的选择）把输入切 chunk，不同 chunk 在流水线的不同节点上同时算。只在流水线 stage 边界通信一次，可与计算重叠；短请求长请求天然通吃，无需动态重组节点

本质是把训练里的 pipeline 并行第一次搬到了推理 prefill 上。选它不是因为理论最快（SP 理论加速比更好），而是因为运维复杂度最低、网络占用最省——这个取舍思路本身就值得学（见 §10 highlight #8）。

4.2 Layer-wise Prefill：让 VRAM 从调度约束里消失

Prefill 是逐层算的、且是计算密集——这意味着每层的 KV 存取可以和计算完全重叠：算第 N 层 attention 前等第 N 层 KV 异步加载完成并预取 N+1 层；第 N 层算完立刻异步写出。全部层算完时，KV 也几乎传完了。

这一步真正买到的东西

不是省了几百毫秒延迟，而是调度器从此可以无视 prefill 节点的 VRAM 余量——KV 即产即走，VRAM 占用时间趋近于零，只要装得下一条请求就行。于是 prefill 选点只剩两个变量：KV 分布 + DRAM 余量。用系统机制消灭一个调度维度，比在调度器里多考虑一个维度高明得多。论文还顺手指出这些空出来的 VRAM 未来可以跑 batch API 这类无 TBT 约束的任务。

5核心调度算法（Algorithm 1 拆解）

这是全文的心脏，也是你说的"magic function"在 Mooncake 里的形态——对每个候选 prefill 节点估一个 TTFT，选最小的；SLO 兜不住就 429 拒绝：

# 对请求 R，遍历每个 prefill 实例 instance： prefix_len = instance 上已有的前缀命中长度 T_queue = 该实例排队中所有请求的 prefill 时间之和 # 排队时间 # 分支 1：本地命中已经够好（best_prefix_len/prefix_len < balancing_threshold） TTFT(instance) = T_queue + T_prefill(len(R), prefix_len) # 分支 2：别处有明显更长的前缀 → 考虑把 KV 从"最佳持有者"传过来 TTFT(instance) = T_transfer(持有者→instance, 差额块数) + T_queue + T_prefill(len(R), best_prefix_len) # 决策： p = argmin TTFT; d = 按负载选 decode 节点 if TTFT > TTFT_SLO or TBT > TBT_SLO: reject R (HTTP 429) # 且：若 best_prefix_len/p.prefix_len > threshold → 顺手把热 KV 复制到 p（热点迁移，见 §6）

三个工程细节决定了它能不能落地：

① T_prefill 是离线标定的预测模型，输入 = (请求长度, 前缀命中长度)。Transformer 计算模式规整，离线数据够多误差就小——这是整个方法可行的地基。

② T_queue 直接拿排队请求的预估 prefill 时间累加——因为 ① 准，所以 ② 才准。所有实例的 TTFT 并行算，调度本身开销可忽略。

③ T_transfer 最难预测（取决于发送端是否拥塞），论文坦承这一点，并把它作为"必须做热块复制"的动机——预测不了拥塞，就用副本消灭拥塞。

映射 → 我们的 DESIGN.md

Algorithm 1 ≈ 我们的 M1（可标定相对 TTFT）+ M2 的 REJECT 分支。centralized_master 的 tokens×1.0 − hit×0.7 + queueTime 是它的线性简化版（缺离线标定、缺 T_transfer、缺 SLO 门槛）。Mooncake 比 centralized_master 多的三样：标定的非线性 T_prefill、显式 T_transfer 项、SLO 硬门槛；比我们 M3 少的：SLO 只是 pass/fail 门槛而非按违约概率定价，路由与淘汰也没合账（cache 池淘汰仍是独立的 LRU/LFU）。

6热点 cache 怎么办：不预测，被动复制

各 prefill 机各管一份本地前缀缓存，使用频率极度不均：system prompt 几乎每个请求都要，某用户的私有长文档只有他自己用。教科书解法是"收集全局使用统计 → 预测未来热度 → 主动放置"。论文明确说：我们试过想过，不行——业务高速增长期 workload 变化太快，预测未来使用量不现实。

他们的替代方案是一套不需要预测的被动启发式，热点复制作为正常调度的副产品自动发生：

规则效果
最佳持有者太忙时，请求被派到别的节点 + 传 KV 过去（Algorithm 1 分支 2）被高频请求的块自动被复制到更多机器——越热的块被"顺手复制"的机会越多
远端最佳前缀 ≤ 本地前缀 × threshold 时，宁可重算不传输避免为一点点增量收益做跨机传输，抑制无谓的复制风暴

实验（8P+8D，重放 23k 真实请求）：KVCache-centric 调度在平均 TTFT 和 TTFT SLO 达成率上同时优于 random 和 load-balancing 两个基线。

阈值的诚实脚注

那个 balancing_threshold 目前是人工调的，论文脚注里承认了并说未来可以自适应。这也是我们 M3 的 V(b) 复制判据（p_reuse × recompute_cost / replicas）可以直接改进的点——把"要不要复制"从手工阈值变成定价。

7过载调度：early rejection 与它引发的振荡

这是全文最有"生产系统味"的一章，三步递进：

7.1 负载的定义就用 SLO 本身

耦合系统里 P/D 互相干扰，TTFT/TBT 难预测，只好用"请求数/容量"这种粗指标。分离之后两阶段独立，Mooncake 直接用 预测的最大 TTFT vs l_ttft、预测的最大 TBT vs l_tbt 当负载定义——负载指标和用户体验指标合二为一，不再有代理指标失真。

7.2 Early Rejection：把 D 的准入判断提前到 P 开始前

问题：P 和 D 的调度之间有时间差。请求 prefill 算完了才被 decode 拒，prefill 全白算。解法很直觉：请求一到就同时看 P、D 两池负载，取更差的那个决定接不接。

7.3 意外：朴素 early rejection 引发反相振荡

上线后观察到 20 台机器的集群里 P 池和 D 池负载反相波动（一个高峰对另一个低谷）。机理是一个经典的反馈延迟问题：

Stage 1: P低D低 → 大量接收 → P 池被打满 Stage 2: 这批 prefill 完成涌入 D → D 高 → 按"当前D负载"拒新请求 → P 池放空 Stage 3: D 池消化完（没有新请求进来）→ D 低 → 又大量接收 → P 又被打满 Stage 4: 循环往复……P/D 交替空转，集群利用率被振荡吃掉

根因：用"当前"的 D 负载去决策"prefill 时长之后"才会到达 D 的请求——控制信号滞后了一个 prefill 周期，形成典型的滞后反馈振荡。

7.4 解法：基于预测的 early rejection

把决策依据从"当前 D 负载"换成"预测的、这条请求 prefill 完成时刻的 D 负载"。预测分两级：

级别思路Mooncake 的选择
请求级预测每条请求的输出长度 → 精确推演❌ 放弃——代价高/精度低，过载时资源最紧张恰恰最需要准
系统级不管单条请求，只估"t 时刻之后整个 D 池的 TBT 水位"：假设每条请求 decode 耗时统一为 t_d，把 t 时刻前 prefill 会完成的请求加进来、执行超过 t_d 的请求移出去，算平均 TBT/l_tbt✅ 粗但稳，持续滚动估计，恰好匹配过载场景对鲁棒性的要求

效果（8P+8D、2 倍速重放模拟过载）：拒绝请求数 4183（基线）→ 3771（early rejection）→ 3589（预测式），即同等资源下多完成约 14% 的请求。

10做得好的地方（9 条 highlight）

Highlight #1 · 把"KVCache 是调度的中心"立成第一性原理

同期工作（Splitwise/DistServe/TetriInfer）都在做 P/D 分离，但都是"算力特性不同所以分开"的资源视角。Mooncake 独有的洞察是：请求怎么路由、块放在哪、谁被淘汰、谁被复制、请求要不要拒——全都是围绕 KVCache 的同一件事。架构图的中心不是 GPU 而是 KV 池。这个视角转换是全文最大的贡献，也直接启发了我们 DESIGN.md 的"一个函数五种决策"。

Highlight #2 · goodput 口径：没跑完 = 全浪费

把"只有完整完成的请求才算数"写进目标函数，一切设计（early rejection、D 侧提前评估、预测负载）都从这个口径里自然推导出来。商业系统的目标函数和论文刷榜的目标函数第一次真正对齐。

Highlight #3 · 用便宜资源换贵资源，而且是"零新增成本"的便宜资源

GPU 服务器上的 CPU/DRAM/SSD/RDMA 本来就闲着。把它们组成分布式 KV 池 = 用已付费但未使用的资源换最贵的 GPU 计算。"Trading more storage for less computation"——会计学上这几乎是无本买卖，工程上只需要一个 Messenger。

Highlight #4 · 负载定义 = SLO 本身，消灭代理指标

不用"请求数/容量"这类代理指标，直接拿"预测 TTFT/TBT vs SLO 门槛"当负载。指标失真（代理指标健康但用户体验崩了）这类生产事故被定义级消灭。前提是分离架构让两阶段延迟可独立预测——架构选择反过来解锁了度量能力，这个联动很漂亮。

Highlight #5 · 发现并解决了一个"没人见过的新问题"：early rejection 振荡

反相振荡这个现象只有真的在 20 台机器上跑过朴素 early rejection 才会看到——这是生产系统反哺研究的典型样本：提出机制 → 上线 → 观察到副作用 → 定位到反馈延迟根因 → 用预测补偿。整个 §7.3-7.4 是控制论里"滞后反馈导致振荡、用预测器补偿"的教科书案例，但在 LLM serving 语境里是首次报告。

Highlight #6 · 知道什么时候放弃预测：两处务实的"不为"

① cache 热度不预测——增长期 workload 不可测，改用被动热点复制启发式；② 请求输出长度不预测——代价高精度低，改用系统级粗粒度预测。在能预测的地方（prefill 时间，计算规整）用尽预测，在不能预测的地方（未来热度、输出长度）果断用启发式——这条"预测能力边界"划得非常清醒，多数论文只会堆更复杂的预测模型。

Highlight #7 · Layer-wise 重叠"消灭调度维度"

逐层异步存取让 KV 即产即走，prefill 调度从此不用考虑 VRAM——用系统机制把一个约束从优化问题里整个删掉，比把它建模进调度器优雅一个量级。副产品（空闲 VRAM 跑 batch API）还顺手指了条商业化路。

Highlight #8 · CPP 的取舍：可运维性 > 理论最优

明知 SP 理论加速更好，仍选 CPP，理由全是生产语言：不需要预建全局通信组、不需要动态调整节点分组、短长请求通吃、网络占用不和 KV 传输打架。论文里少见地把"弹性伸缩太复杂"当成一等否决理由——这是运维过大集群的人才写得出的判断。

Highlight #9 · 开源 trace + 全程诚实

第一个可做真实复用分析的公开 trace（我们的模拟器直接受益）。此外论文里的诚实密度很高：threshold 是手工调的（脚注承认）、线上复用率远低于开源 benchmark（Related Work 直说）、[2P+2D] 配比会输给基线（负结果照登）、T_transfer 难预测（坦承）。这些"自曝"让所有正面数字都更可信。

11可挑战之处 & 与我们设计的映射

11.1 可挑战 / 可超越的点

论文的选择局限我们 DESIGN.md 的对应改进
SLO 是硬门槛（超了就 429） 所有没超线的方案被视为等价，无法表达"离违约多近"；不同 tier 请求无差别对待 M2：SLO 归一化 slack + 违约概率定价（λ_ttft·P[TTFT>slo]），紧 SLO 请求自动获得亲和优先权
路由用 TTFT 打分，但 cache 池淘汰仍是独立的 LRU/LFU 路由和淘汰两本账——恰是我们批判 Turbo 的"策略分家"在 Mooncake 身上的残留 M3：块价值 V(b) 统一路由外部性与淘汰，合成一本账
热点复制阈值手工调 论文自己承认；阈值全局一个，不分块 V(b) 的 replicas 分母天然给出 per-block 复制判据
系统级负载预测假设 decode 耗时统一 t_d 粗；输出长度分布重尾时误差大 M2 用校准残差的经验分位数做 risk 项（§7 pingpong 议题 2）
D 侧仍有 double-check 拒绝（prefill 白算通道没有完全堵死） early rejection 降低了概率但未消灭 DESIGN.md §4.3 路径 B（Gated-PD 测量式 probe）/ 路径 D（Store 化结构性消解）
