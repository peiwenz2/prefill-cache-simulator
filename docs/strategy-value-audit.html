0.4 Idle TTL：准确 assumptions

不是 Mooncake benchmark
  1. Capacity infinite，没有 capacity eviction。
  2. Idle expire：now-last_access > TTL 才过期。
  3. Hit renew：命中刷新 last access，等价于 LRU recency refresh。
  4. Strict prefix：第一个过期／缺失后停止。
  5. Instant insert：lookup 后按 trace timestamp 立即写入，不模拟 completion visibility。
  6. Single global namespace：没有 per-GPU placement 和 KVT cost。

1总体架构：先从零理解问题

30 秒版本
  • Prefill 把输入 prompt 算成 KV 状态；Decode 用这些状态逐 token 生成答案。
  • 长 prompt 的 prefill 很贵；新请求若共享旧请求的开头，可以复用 prefix KV blocks。
  • 每台 prefill node 的 local cache 不一样。相同 prefix 被发到不同 node，集群明明算过，当前 node 仍会 miss。
  • Selector 必须同时优化 reuse 与 queue：只追 hit 会形成 hotspot，只追最闲会打散 cache。
同一个 block 可能同时存在于多台 node；稳定 owner 减少副本，但热 owner 也可能排队。
先给结论
  1. 这份 trace 的 exact-prefix workload ceiling 是约 51%～57%，不是 90%；论文与本仓口径不同，禁止直接横比。
  2. 没有无条件 winner：100ms delayed view 下 S3 hit 最高；fresh view 下 S5 同时拿到更高 hit 与更低 queue。
  3. 生产上最值得验证的是“fresh view 用 cost score，stale view 用 stable ownership”，再用 overload gate 与 bounded choice 连接两者。
  4. 最值钱的长期方向是 KVS／SLO-aware request lifecycle，而不是单独追 hit。
  5. 当前模型适合策略排序，不等于 Mooncake hardware reproduction。

先回答最容易误会的地方

精确映射
S3 就是 selectors.py:182-194 的 gb_prefix_bucket_selector()：PrefixAnchor(k=2)＋CapacityGate(1.25)＋logical ring 上两个 secondary candidates 的 BoundedFallback。
相同 prefix 回到 stable owner，replica factor（同一 block 平均存在于几台 node；1.0 表示没有重复副本）降到 1.045；热 owner 也导致 load max／mean=1.822。
图里的词翻译成人话不是

2.1.3 S4 SessionAffinity：没有 session_id 怎么做

S4 使用 OnlineConversationLinker，不是读取真实 session。它只看过去请求：最长共享 prefix 匹配 family；排除公共 hot-only blocks；family 到 cap 后切开；再 sticky 到 owner。M4 得到 53.34% hit、load max／mean 1.047、queue p95 3011：用 0.67pp hit 换掉 S3 的严重偏斜。

  1. 要求至少共享配置给定的 minimum prefix blocks，避免只凭一个公共块合并。
  2. 每 256 个请求按 P99 刷新 hot threshold，hot-only prefix 不作为会话证据。
  3. M4 family cap=128；达到上限后切新 family，避免单个热家族霸占 node。
  4. 线上应把 proxy 换成 privacy-safe hashed session key；当前结果不能叫真实 session 收益。
参数M4 值作用来源／风险
minimum_shared_blocks2至少共享前 1,024-token block boundaries 才考虑同 family。preset；不是 trace 的真实 session label
family_size_cap128一个 inferred family 满 128 requests 后切新 family，限制热点。跑过 8／32／128／512 sensitivity
hot_block_percentile99只由超热公共 blocks 构成的 prefix 不作为 session 证据。每 256 requests 在线刷新；跑过 90／95／99／100
stickytrue同 family 尽量回上一次 owner；owner 过载仍可 break。production 应换 privacy-safe real session key

2.1.4 S5 Centralized Master TTFT：为什么中心化策略看起来较差

load = running_tokens + queued_uncached_tokens
score = load + input_tokens - 0.7 × estimated_local_hit_tokens

主因不是公式，而是 stale-view herding。S5 在 fresh view 下同时拿到更高 hit 和更低 queue；50ms 后 queue 已放大 5.4 倍。

2.1.5 S6 CalibratedTTFT：校准 score，没有校准 freshness

uncached = input_tokens - hit_tokens
score_ms = (queue_tokens + uncached) × prefill_uncached_token_ms

S6 把 S5 的经验折扣 0.7×hit 换成带物理意义的 prefill_uncached_token_ms；M9-HW 得到真实 coefficient 后可以直接替换。 M4 hit=53.37%、load max／mean=1.269，但 queue p95 仍为 6393。 它改善了 score 的可标定性，没有修复输入 freshness。

名字里有 Calibrated，不代表已硬件校准
M4 使用 0.0568 normalized ms／uncached token，它是 synthetic service coefficient。只有 M9-HW 用真实 engine 测出 prefill／KVT／overlap 后，score 才能称为 hardware-calibrated TTFT。

  • S5=52.32%、S6=53.37%；S3 相对 production-style simulator baseline 只有约 0.6～1.7 pp。
  • S4 用约 0.67 pp hit 代价，把 load max/mean 从 1.822 降到 1.047；这才是主要 trade-off。
  • Production headroom 仍是 NOT_MEASURED，必须由 R1 shadow 给出。
敏感性实锤
  • lambda_risk=2.0 时 P2=0.4437，低于 P0=0.4883。
  • 2 个 D nodes 时 D1=0.6235，低于 D0=0.6846。
  • migrate_on_boundary=True 时 D1 跌到 0.00153。
  • Deploy candidate 更像真实 session_id 版 S4；S3 保留为 locality ceiling probe。
最值钱

Cache-aware request lifecycle，而不是 cache-aware selector。

  1. Prefix routing 已接近 workload ceiling；有限 local 与无限 global 的 3.06 pp 差距只作参照。
  2. Mooncake Algorithm 1 本身也在比较 queue、prefill、transfer 与 SLO，而不是只选最长 prefix。
  3. 你的设计把 WHERE 留给现有 Global Batching／Centralized Master／Turbo，把 attempt、lease、checkpoint、output authority 和 retry budget 留给 client。
  4. Admission gating＋归属分离有 replay／protocol 证据；remote 五元比价主要是 Algorithm 1 类比＋架构推理；D2 未验证。
  5. 同一套 ledger 最终可以回答：发哪台 P、KV 从哪里来、D 是否继续占用、失败后从哪里恢复。
不能相加
S3 locality＋KVS＋SLO gate＋decode lease 的收益不能直接相加。KVS 让 selector 不必为命中粘死热点；SLO gate 判断 transfer 是否值得；lease 只在压力下减少 HoL。它们是一个控制闭环的不同环节。

5.1 M12 final：54 个 cell 最终说明了什么

一句话结论
M12 不是“Decode gate 获胜”的证明，而是一次完整的 falsification： 只追 cache hit 会输掉 completed goodput。在 MIXED 1.5×， Decode Causal 把 token hit 从 Priced Spill 的 57.06% 提到 76.11%； strict output goodput 则相对同一修复代码重跑的 Decode No-Gate 从 0.14036 降到 0.12696，下降 9.55%。

5.1.1 先拆开 54：不是 54 种可以上线的策略

组成怎么算它回答什么能否部署

3 个 regime 是什么
  • COMPUTE_BOUND：prefill／decode 计算先成为瓶颈。
  • MEMORY_BOUND：KV capacity／memory price 更重要。
  • MIXED：计算、内存和 queue 同时竞争；最接近我们想找的系统级冲突。
5 个 scale 是什么
  • 0.8×、1.0×、1.2×、1.5×、2.0× 是同一 trace 的 offered-load 倍率。
  • 它不是 GPU 数，也不是模型 batch size。
  • 1.5× 是预先选择的 overload sensitivity 点，不是看到结果后再挑的最好 case。
最容易读错的地方
  • Token hit 高，不等于完成更多请求。retry 可以再次访问相同 prefix，从而把 hit 数抬高。
  • Queue p95 不是毫秒。它是 frozen simulator 的 normalized work。
  • Strict output goodput 不是 requests／s。它只用于同一 experiment contract 内比较 SLO 内完成的 output work。
Causal、Oracle、gated 分别是什么意思
  • Causal：只用当前时刻已经发生、已经可见的信息做 gate 决策，不偷看未来。
  • Oracle：能看到未来结果，只用于测“信息完美时的理论上界”，不能部署。
  • Credits：decode admission 名额的记账；名额不足时 gate 可以拒绝 attempt。
  • Gated：被 gate 拒绝进入 decode、需要重新排队的 attempt。一次请求可 retry 多次，所以它不是 unique request 数。

5.3 Kill／narrow criteria

  1. R1 若显示 production baseline headroom＜2 pp 且无 load-skew 空间，关闭 WHERE enforcement 线。
  2. M12.0 已触发 hard kill：停止 router hold；不否定 Priced Spill／placement locality／engine batching。
  3. M12.1 已冻结 tier≥0.80、Jain≥0.90、relative regression≤0.02。
  4. M12.2 的等价判定容差（epsilon）冻结为 hit 0.1pp、max／mean +0.05、P queue p95 +5%；小于容差视为打平。
  5. M12.3 已触发 narrow：MIXED 1.5× 下 strict output goodput 相对 no-gate 下降 9.55%，因此只保留 overload-only，不进入常态部署。
  6. normalized simulation 可以 kill；pass 只算 provisional。M12-HW 前禁止发布 MFU。
