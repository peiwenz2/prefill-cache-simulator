0.4 Idle TTL：准确 assumptions

不是 Mooncake benchmark
  1. Capacity infinite，没有 capacity eviction。
  2. Idle expire：now-last_access > TTL 才过期。
  3. Hit renew：命中刷新 last access，等价于 LRU recency refresh。
  4. Strict prefix：第一个过期／缺失后停止。
  5. Instant insert：lookup 后按 trace timestamp 立即写入，不模拟 completion visibility。
  6. Single global namespace：没有 per-GPU placement 和 KVT cost。

0.5 数据集能否判断 session

回答
不能确定真实 session，只能推断 prefix family proxy。论文说采样时优先保留同 session 请求，但没有把 session label 放进 trace。
现象为什么不能等同 session
共享长 prefix可能是同一 conversation，也可能是不同用户使用同一文档
共享第一块depth=1 只有 4 families，最大 10,938 requests，主要是公共 system prompt
prefix 不同同 session 也可能因 template／截断变化而 false split
相同 timestamp22,428 个 adjacent same-time pairs，无法恢复毫秒内真实顺序

S4 的 OnlineConversationLinker 只用历史 prefix，要求 minimum shared blocks，排除 hot-only prefix，并限制 family size（affinity.py:37-114）。它是 causal proxy；线上应换成 privacy-safe hashed session key。

1总体架构

先给结论
  1. 这份 trace 的 exact-prefix workload ceiling 是约 51%～57%，不是 90%；论文与本仓口径不同，禁止直接横比。
  2. 当前最确定的收益来自恢复 prefix locality：S3 比 Random 增加 9.71 pp。54.01% 是有限多节点 local，57.07% 是无限单池，94.6% 只作空间参照。
  3. 最值钱的不是某一个 selector，而是 KVS／SLO-aware request lifecycle；admission gate 与 ownership boundary 证据最强，remote／D2 尚弱。
  4. Decode lease 目前只证明能救单 D node 病理 HoL，不是 always-on winner。
  5. 当前模型适合策略排序，不等于 Mooncake hardware reproduction。

3关键技术评估

3.1 收益排行榜

#能力最大观察收益证据判断

Production baseline 错配警告
  • +9.71 pp 只相对 Random，禁止当作线上收益。
  • S5=52.32%、S6=53.37%；S3 相对 production-style simulator baseline 只有约 0.6～1.7 pp。
  • S4 用约 0.67 pp hit 代价，把 load max/mean 从 1.822 降到 1.047；这才是主要 trade-off。
  • Production headroom 仍是 NOT_MEASURED，必须由 R1 shadow 给出。
敏感性实锤
  • lambda_risk=2.0 时 P2=0.4437，低于 P0=0.4883。
  • 2 个 D nodes 时 D1=0.6235，低于 D0=0.6846。
  • migrate_on_boundary=True 时 D1 跌到 0.00153。
  • Deploy candidate 更像真实 session_id 版 S4；S3 保留为 locality ceiling probe。
最值钱

Cache-aware request lifecycle，而不是 cache-aware selector。

  1. Prefix routing 已接近 workload ceiling；有限 local 与无限 global 的 3.06 pp 差距只作参照。
  2. Mooncake Algorithm 1 本身也在比较 queue、prefill、transfer 与 SLO，而不是只选最长 prefix。
  3. 你的设计把 WHERE 留给现有 Global Batching／FlexLB／Turbo，把 attempt、lease、checkpoint、output authority 和 retry budget 留给 client。
  4. Admission gating＋归属分离有 replay／protocol 证据；remote 五元比价主要是 Algorithm 1 类比＋架构推理；D2 未验证。
  5. 同一套 ledger 最终可以回答：发哪台 P、KV 从哪里来、D 是否继续占用、失败后从哪里恢复。
不能相加
S3 locality＋KVS＋SLO gate＋decode lease 的收益不能直接相加。KVS 让 selector 不必为命中粘死热点；SLO gate 判断 transfer 是否值得；lease 只在压力下减少 HoL。它们是一个控制闭环的不同环节。

5.1 Kill／narrow criteria

  1. R1 若显示 production baseline headroom＜2 pp 且无 load-skew 空间，关闭 WHERE enforcement 线。
